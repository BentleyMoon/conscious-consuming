Spec / open-values-design-token-index

Open Values Design Token Index v0.1

A generated copy of the design tokens with CSS custom properties, computed colour contrast results, and counts of how many catalogue options can be drawn as a value bloom. A build script makes it from content/design/tokens.json, at the same time writing the token values into the app stylesheet, and the design audit reads it.

  • Files built from other files
  • Status: draft
  • Version: 0.1.0
  • Format name in the file: open-values-design-token-index

Draft. It may still change before it is called stable. A file a build step makes from other files. Change the sources, not this file.

Who writes it and who reads it

Written by pipeline/build_design_tokens.js. Read by future app skin loader, audit:design-tokens, preview QA.

Fields

FieldWhat it meansType
format requiredNames the file format. Always open-values-design-token-index.always "open-values-design-token-index"
version requiredThe version of this format the file follows. Currently 0.1.0.string
standard requiredThe standard this file belongs to. Always open-values-standard.always "open-values-standard"
built requiredThe date of the index, as YYYY-MM-DD, copied from the updated date of the tokens file.see date
purpose requiredA sentence saying what the index is for.see nonEmptyString
generatedFrom requiredThe tokens file the index was built from, with its date and hash, so a stale index can be detected.object
principles requiredThe design rules from the tokens file, copied unchanged.list
referencesThe outside documents from the tokens file, copied unchanged.list
valueBloom requiredThe value bloom section from the tokens file, plus how many catalogue options can be drawn as a bloom and three example options to preview it with.see valueBloom
valueSignatureCoverage requiredThe same counts as valueBloom.signatureCoverage: how many catalogue options have theme scores and stored signatures.see valueSignatureCoverage
cssVariableMapping requiredThe token to CSS custom property table from the tokens file, copied unchanged.see cssVariableMapping
contrastRemediationContractThe contrast fix checklist from the tokens file, copied unchanged.see contrastRemediationContract
skinReadiness requiredWhether the data the app needs for each part of the skin (palette, day cycle, motion, value bloom, materiality) is in place. Ready here means the data exists, not that the app has been checked visually.see skinReadiness
counts requiredTotals across the whole index.see counts
filters requiredSorted lists of the ids that appear in the index, for building filters and checks.object
profiles requiredEvery profile from the tokens file, flattened for the app, with the CSS custom properties it produces and its computed contrast results.list

A reader MUST ignore fields it does not know, so a file can carry more than this list and still be read. A writer MUST NOT change what a listed field means.

The schema

Its address is https://openvaluesstandard.org/schema/design-token-index-v0.1.schema.json. Validators can fetch it there; the file is also in the repository at app/data/standard/schemas/design-token-index.schema.json.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as described in RFC 2119 and RFC 8174 when, and only when, they appear in capitals.

Whether this format fits your app is your call. The spec says what a file MUST hold. Which formats you read and write, and what your app does with them, is yours to decide.

Generated from the registry, the schemas and the conformance examples, so it matches them exactly.
